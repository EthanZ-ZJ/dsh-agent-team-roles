# ADR 模板与判定

> 用途：写 ADR、用 Y-statement 记录小决策、判断某个选择到底该不该写 ADR。
> 方法来源：Nygard ADR、MADR minimal、AWS/Azure ADR 指南。全部离线，直接复制填空。

## 一、先判定：要不要写

命中任一 → 写 ADR：

- [ ] 难以反转：公共 API、协议、持久化格式、数据模型、云厂商或关键依赖。
- [ ] 跨团队契约：本团队之外有人依赖它。
- [ ] 成本或合规/安全有显著影响。
- [ ] 团队对同一问题争论超过一轮。
- [ ] 方案被否决：记录否决理由，防止重复争论。
- [ ] 引入/移除一个长期基础设施组件。

都不命中 → 不写 ADR，写「约束记录」（见 `tradeoff-matrix.md` 末节），并在汇报里说明「为什么不需要 ADR」。

## 二、MADR minimal（默认，复制后逐项填）

```markdown
# ADR-NNNN：<一句话写清选了什么>

- 状态：提议 | 已接受 | 已拒绝 | 已被 ADR-MMMM 替代
- 日期：YYYY-MM-DD
- 决策人：<Lead/用户/SE + 角色>
- 置信度：高 | 中 | 低

## 背景与约束

- 要解决什么问题，为什么现在要决定（1–3 句）。
- 约束：引用 ASR 编号 / 硬约束 / 合规要求。
- 不确定性：哪些信息还不确定，影响哪个选项。

## 备选

1. **<选项 A>**：做法一句话。优点 / 缺点 / 放弃原因（若不是它）。
2. **<选项 B>**：做法一句话。优点 / 缺点 / 放弃原因。
3. **维持现状**：代价是什么，为什么不够。

## 决定与理由

选 <选项>。理由 1/2/3（每条对应一条 ASR 或约束）。

## 后果

- 正面：…
- 负面（必须写）：…
- 接受的代价与风险：…（引用风险登记条目）
- 受影响方与需要的后续动作：DEV / TSE / CR / CI/CD 各要做什么。

## 重审触发

出现 <信号> 时重审本条决策（例：QPS 超过 X、团队规模超过 Y、云厂商降价/涨价、依赖进入 EOL）。
```

## 三、Y-statement（小决策，一行）

```text
在 <背景> 下，面对 <关注点>，我们选择 <选项>，以获得 <收益>，接受 <代价>。
```

示例：

```text
在 日活 < 1 万且单库写入 < 500 TPS 的背景下，面对 读扩展 的关注点，我们选择 只加只读副本，以获得 一周内可上线且不改数据模型，接受 写容量上限与主库单点风险（重审信号：写入 > 800 TPS 持续一周）。
```

要求：必须含「获得」和「接受」两段。只能写「获得」的是宣传稿，不是决策记录。

## 四、生命周期规则

- **只增不改**。已接受的 ADR 不回改；新决定写新 ADR，状态标「已被 ADR-MMMM 替代」，旧记录保留。
- **一个 ADR 一个决策**。多阶段决策拆成多条，按依赖顺序链接。
- **ADR 不写接口细节**。字段、错误码、兼容窗口放契约文件；ADR 写契约的权威路径。
- **ADR 不写设计指南、不写会议纪要**。设计文档放 `docs/design/`，ADR 只回答「为什么这样定」。
- **低置信度也落盘**。标「低置信度」+ 重审触发，比假装确定安全。
- **被拒绝的 ADR 保留**。状态「已拒绝」并写理由，避免下一轮重复争论。

## 五、质量门槛（写完逐条打勾）

- [ ] 标题能否独立读懂「选了什么」，不读正文也成立？
- [ ] 备选是否包含「维持现状」，且每个被拒选项都有具体放弃原因（不是「不合适」）？
- [ ] 后果是否写了负面项？只有好处的 ADR 视为未完成。
- [ ] 是否引用了 ASR 编号 / 约束 / 风险条目，而不是空泛理由？
- [ ] 是否有置信度与重审触发条件？
- [ ] 是否与契约文件重复？重复部分是否改成引用路径？

## 六、反例（出现即改写）

- 「决定采用微服务架构」——没有背景、没有备选、没有代价：改成具体边界决策，或删。
- 「因为业界最佳实践」——补适用条件、反例、本项目的证据。
- 把整篇设计文档贴进 ADR——拆成 ADR（为什么）+ 设计文档（怎么做）。
- 回改已接受 ADR 的结论——新写一条并 supersede。
