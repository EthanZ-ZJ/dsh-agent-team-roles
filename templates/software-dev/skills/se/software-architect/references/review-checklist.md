# 评审与交接清单

> 用途：方案自检、评审他人方案、向 CR/DEV/TSE/Lead 交接前逐项打勾。
> 全部为静态检查项，不需要脚本或网络。

## 一、方案自检 12 条（交付前）

- [ ] 1. 档位判定有依据？降档有约束记录？
- [ ] 2. 任务卡 6 行齐全（输入/影响面/档位/产出/决策人/未决）？
- [ ] 3. 每条质量要求都转成六要素场景，带 response measure？
- [ ] 4. ASR 3–7 条，每条有来源与协商性？
- [ ] 5. Non-goals ≥3 条且带原因？
- [ ] 6. 现状图与目标图分开标注，事实/推断/假设有来源？
- [ ] 7. L3 有 ≥2 个真实选项 + 矩阵 + 置信度 + 重审触发？
- [ ] 8. 每个接口契约有唯一权威路径、版本策略、失败例？
- [ ] 9. 数据四问齐（system of record / 一致性 / 失败模式 / 迁移回滚）？
- [ ] 10. 风险登记每条有触发信号与负责人，无「暂无」？
- [ ] 11. ≥1 个可自动化 fitness function 候选，已指定交 TSE？
- [ ] 12. 交接包有契约路径、任务边界、未决问题与决策人？

## 二、C4 图检查（10 条）

- [ ] 1. 图有标题、类型（Context/Container/…）、范围、图例？
- [ ] 2. 每个元素有名字、类型、职责？
- [ ] 3. 每条箭头有意图标签（动词 + 目的），不只是「调用」？
- [ ] 4. 箭头标了方向、同步/异步、协议或事件名？
- [ ] 5. 外部系统与团队不可控依赖被标出？
- [ ] 6. 数据存储标注了所有者（谁写）？
- [ ] 7. 现状与目标态没有混在同一张图？
- [ ] 8. 图与代码/配置一致，不一致处标了「待核实」？
- [ ] 9. 图回答了某个具体问题（「改动会影响谁」或「故障传到哪」）？
- [ ] 10. 没有为了好看而加的装饰元素或未解释的颜色/线型？

## 三、契约检查（8 条）

- [ ] 1. 唯一权威文件路径写清，其他位置只引用？
- [ ] 2. 输入/输出、必填/可选、缺失 vs 空 vs 默认值写清？
- [ ] 3. 错误码/错误语义/可重试性写清？
- [ ] 4. 异步接口写了幂等、重复、乱序、超时、积压？
- [ ] 5. 版本与兼容策略写了（新增/弃用/破坏性）？
- [ ] 6. 破坏性变更是否已开 ADR？
- [ ] 7. 有一个正常例 + 一个失败/边界例？
- [ ] 8. 消费者清单与通知动作写清？

## 四、数据检查（6 条）

- [ ] 1. system of record 唯一写入方是谁？
- [ ] 2. 一致性选择与冲突解决规则写清？
- [ ] 3. 分区/超时/重复/部分失败的行为与恢复路径写清？
- [ ] 4. 迁移按扩展→迁移→收缩排，有回滚点与停止信号？
- [ ] 5. RPO/RTO 与备份/恢复演练方式写清？
- [ ] 6. 缓存失效策略与一致性窗口写清？

## 五、演进检查（4 条）

- [ ] 1. 每个 L2+ 至少 1 个可自动化 fitness function（度量 + 阈值 + 交给谁）？
- [ ] 2. 演进路线有接缝、共存期、批次、停止信号？
- [ ] 3. 没有大爆炸替换？
- [ ] 4. 技术债条目有偿还触发条件？

## 六、评审他人方案：问题清单

先静默阅读 10–15 分钟，再逐条问；不替作者重写，不把风格偏好当阻塞项。

1. **为什么不是 B？** 备选被排除的真实原因是什么？
2. **代价是什么？** 这个选择放弃了什么质量属性或能力？
3. **什么条件下要重审？** 有信号和阈值吗？
4. **谁受影响？** 下游消费者、运维、合规、TSE 都知道吗？
5. **数据归谁？** 有没有跨服务写同一份数据？
6. **失败时怎样？** 依赖挂了、消息重投、迁移中断时系统表现如何？
7. **怎么验证？** 每个 ASR 有可执行验收吗？fitness function 能自动化吗？
8. **有没有第二份手抄清单？** 同一字段/错误码是否在 ≥2 处定义？

输出格式：

```text
[必须改] <条目> — 违反 <契约/ASR/数据规则> — 建议 <动作>
[建议改] <条目> — 原因 — 可选动作
[问题] <需要作者/Lead 回答的问题> — 不回答的后果
```

区分「必须改」与「建议改」；不写「感觉不太好」。

## 七、交接清单

### 交 DEV

- [ ] 按契约边界拆的任务清单（不是按文件数拆），标顺序与依赖。
- [ ] 契约权威路径（DEV 动手前必须先读）。
- [ ] 禁止事项（不许改的接口、不许绕过的一致性规则）。
- [ ] 验收点（DEV 自测能判断通过与否）。
- [ ] 不确定/未决项及找谁仲裁。

### 交 TSE

- [ ] 质量属性场景表（每条带前置/操作/预期）。
- [ ] 边界与失败用例清单。
- [ ] fitness function 候选（度量 + 阈值 + 建议实现方式）。
- [ ] 哪些点无法自动验证，需要人工或环境支持。

### 交 CR

- [ ] 契约条目 ↔ diff 对照点。
- [ ] 必须改 / 建议改分级。
- [ ] 静态可查项（字段名、错误码、版本字段、生成区标记）。

### 给 Lead 的决策请求（≤15 行）

```text
背景：<一句>
建议：<方案>，理由 1/2/3
备选：<方案 B>，放弃原因 <一句>
代价与风险：<一条最关键的>
需要您决定：<具体问题 + 选项>
不决定的后果：<延迟成本 / 风险敞口>
```

## 八、评审反模式

- 替作者重写方案——改成提问与建议。
- 把风格偏好当阻塞项——标注「建议」。
- 只挑毛病不给优先级——分级。
- 评审变成宣讲——先静默阅读，再讨论。
- 越权宣布「评审通过/测试通过」——结论归 CR/TSE，SE 只给可验证点。
