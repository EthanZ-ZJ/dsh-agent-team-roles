# 质量属性场景（ASR → 可测场景 → TSE 用例）

> 用途：把「要快/要稳/要安全/要省」变成可测场景，并直接派生成 TSE 可执行的验收用例。
> 方法来源：SEI 质量属性场景与 QAW、ATAM utility tree、Azure/AWS Well-Architected 维度。离线可复制。

## 一、六要素

| 要素 | 含义 | 反例（缺了会怎样） |
|---|---|---|
| source | 谁/什么触发（用户、定时任务、外部系统、攻击者） | 「系统要快」——不知道谁在什么负载下 |
| stimulus | 触发的事件（请求、故障、配置变更、攻击） | 「性能要好」——不可测 |
| environment | 触发时的运行状态（正常、峰值、降级、分区、冷启动） | 漏掉峰值或故障态，验收永远在理想态通过 |
| artifact | 被影响的部件（接口、服务、存储、整个系统） | 不知道改哪个部件 |
| response | 系统应如何响应（返回、降级、拒绝、告警、恢复） | 只知道「不能慢」 |
| response measure | 可测度量（P95/P99 延迟、错误率、RTO/RPO、恢复时间、成本/请求） | 没有数字，无法 pass/fail |

## 二、一行模板

```text
当 <source> 在 <environment> 下触发 <stimulus> 时，<artifact> 应在 <response measure> 内 <response>。
```

**示例（性能）**：

```text
当 移动端用户在 晚高峰（1000 QPS）下 打开订单列表 时，订单服务 应在 P95 < 300ms、错误率 < 0.1% 内 返回前 50 条订单（分页游标）。
```

**示例（可用性/恢复）**：

```text
当 主数据库在 单可用区故障 下 不可写 时，订单服务 应在 30 秒内 切换只读降级并向用户显示明确提示，RTO ≤ 5 分钟、RPO ≤ 1 分钟。
```

**示例（安全）**：

```text
当 未认证请求在 任意环境 下 访问 /admin/* 时，网关 应在 100% 情况下 返回 401/403 且不泄漏资源是否存在，并产生一条审计日志。
```

**示例（成本）**：

```text
当 日活为 5 万 时，导出功能 的单次全量导出成本 应 ≤ 0.05 元，且不触发对象存储的跨区流量计费。
```

**示例（可运维）**：

```text
当 发布新版本在 生产 下 出现 5xx 上升 时，值班人员 应能在 3 分钟内 从仪表盘定位到具体服务与版本，并能一键回滚到上一版本。
```

## 三、七维度检查表（每个 L1+ 需求至少扫一遍）

| 维度 | 要问的场景 | 常见漏项 |
|---|---|---|
| 性能 | 峰值/长尾/大请求体/批量 | 只测平均值，不测 P95/P99 |
| 可用性 | 依赖故障、分区、重启、冷启动 | 没写降级行为与恢复目标 |
| 可运维 | 发布、回滚、定位、告警 | 没写「出问题 3 分钟内怎么知道」 |
| 安全 | 认证、授权、注入、越权、审计 | 只写「要安全」，不写具体攻击面 |
| 成本 | 单位成本、增长曲线、存储/流量 | 只算一次性，不算持续 |
| 可演进 | schema/协议兼容、灰度、数据迁移 | 没写旧版本共存期 |
| 合规 | 数据保留、出境、审计、脱敏 | 当成「以后再说」 |

不是每个维度都要写满：不适用的标注「不适用，理由」；不确定的标注「假设，待确认 + 谁确认」。

## 四、坏 → 好 改写

| 原始需求 | 问题 | 改写 |
|---|---|---|
| 「导出要快」 | 无 source/environment/measure | 当 运营在 后台 触发 10 万行订单导出 时，系统应在 60 秒内 生成下载链接，超过 5 分钟的任务转为异步并通知。 |
| 「要高可用」 | 无故障模型、无 RTO/RPO | 当 单可用区故障 时，核心下单链路应在 5 分钟内 恢复写能力，RPO ≤ 1 分钟。 |
| 「要能扩展」 | 无规模与成本 | 当 日活从 1 万增长到 10 万 时，无需改数据模型即可水平扩展读能力，单位请求成本增幅 ≤ 20%。 |
| 「要安全」 | 无攻击面 | 当 普通用户 尝试 访问他人订单详情 时，系统应 100% 返回 403 且记录审计日志，不泄漏订单是否存在。 |

## 五、排序与裁剪

1. 场景生成：每个 stakeholder 关注点写 1–3 条，宁可多写再合并。
2. 合并去重：同一 artifact + 同一 stimulus 的合并。
3. 投票排序：由 Lead/PM 对「业务重要性 × 实现难度」排序，取 top 4–5 作为本轮 ASR。
4. 未入选场景：写进「暂缓场景」并注明原因，不要删除（下轮可能用）。

## 六、派生成 TSE 用例

每条场景至少给 TSE 三行：

```text
场景：ASR-2（晚高峰订单列表 P95 < 300ms）
前置：数据集 100 万订单，用户 1000 并发，缓存冷启动
操作：持续 10 分钟请求列表接口（含分页）
预期：P95 < 300ms，错误率 < 0.1%，无 5xx；超阈值时输出分位分布与慢请求样本
```

规则：

- 场景里的每个数字都要能映射到「测什么、怎么造数据、看哪个指标」。
- 无法自动化的场景标「人工验收」并写步骤与证据要求。
- 场景变更要通知 TSE（已写好的用例会失效）。

## 七、反例（出现即改写）

- 形容词当需求：高性能、高可用、易扩展、安全可靠——全部改写为六要素。
- 只写正常态：漏掉峰值、降级、故障、冷启动。
- 目标数字无来源：标「假设」并写谁来验证，不静默编数。
- 一条场景塞多个 artifact 或多个不相关刺激——拆开。
