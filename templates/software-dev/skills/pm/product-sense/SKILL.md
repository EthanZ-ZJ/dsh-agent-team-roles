# 产品经理工作法（product-sense）

蒸馏自 pm-skills（https://github.com/product-on-purpose/pm-skills ，Apache-2.0）的
deliver-prd / define-problem-statement / define-prioritization-framework /
deliver-user-stories 四个技能，按本团队流程（只读 + 文本产出、契约交给 SE）改编。

## 何时加载

- 要写需求文档 / PRD / 用户故事 / 验收标准
- 要做调研并把结论整理给 Lead
- 要在多个候选需求之间做优先级排序或取舍

## 一、问题框定（写任何文档前先过这关）

1. **用户段要具体**："用户"不是答案。写成"移动端结算页的买家"或"管理 50+ 成员的团队管理员"。
2. **痛点要有证据**：来自访谈、工单、行为数据或仓库内讨论记录，标注出处；没有证据就标为假设。
3. **量化影响**：影响 = 谁受影响 + 多严重 + 多频繁；给出数字或合理的估计区间。
4. **只说 what，不说 how**：问题陈述禁止出现实现方案；方案是 SE 契约的事。
5. **回答 why now**：为什么值得现在投入，而不是下个季度。
6. **成功指标带基线和目标**："转化率从 2% 提升到 3%（一个发布周期内）"，不是"提升体验"。

## 二、调研综合（访谈、竞品、反馈归纳）

- **分主题归纳，不流水账**：把原始材料归纳成 3–5 个主题，每个主题附代表证据和来源数量。
- **区分事实 / 推断 / 假设**，三种标签在文档里显式出现；没有把握的结论降级为假设并写验证方式。
- **竞品对比聚焦差异与启示**：不止罗列功能，回答"它验证了什么需求、我们的机会在哪"。
- **小样本就是方向性的**：访谈 <5 人、问卷 <30 份只能得出方向性结论，禁止写成"已验证"。
- **不编造数据**。缺输入时写"未知，待确认"，或列出补齐数据的具体问题清单交给 Lead。

## 三、优先级排序（多框架互查，拒绝拍脑袋）

- **候选 ≥3 项才有排序意义**；少于 3 项直接做决定，不要走流程。
- **多个框架并行打分**：RICE（Reach×Impact×Confidence÷Effort）、ICE（粗估 1–10）、
  MoSCoW（Must/Should/Could/Won't）按数据可得性选用；多框架一致 → 置信高；
  **框架间分歧本身就是发现**——说出是哪个维度在拉扯。
- **每个分数可追溯到输入或显式标注为假设**，禁止静默编数。
- **输出建议 + 下一步**，不是只有排名：先做什么、缓做什么、什么数据会改变结论。

## 四、需求文档（PRD）结构

按序组织， feature 不需要的节可省略，但**不许留空节**：

1. 问题概述（含 why now）
2. 目标与成功指标（基线 → 目标，可测量、有时限）
3. 用户故事（见下节）
4. 功能需求（每条可测试：有人能判定满足/不满足）
5. 范围边界（明确 in / out / future 三栏，防蔓延）
6. 技术考量（只列约束与集成点供 SE 参考，**不做方案设计**）
7. 依赖与风险（每条带缓解思路和责任人）
8. 调研摘要（出处 + 可信度；见第二节）
9. 开放问题（未决事项和需要的决策）

**执行契约视角**（本团队强制）：文档会被无上下文的成员执行。写完自查——
每条需求谁验证、以什么为准；两份材料冲突时以哪份为准；执行者在什么情况必须停下来问 Lead
而不是自己拍板。验收标准用 Given/When/Then，每条都能独立判 pass/fail。

## 五、用户故事

- 格式：作为〈具体用户段〉，我要〈动作〉，以便〈收益〉。**收益句不可省**——它支撑优先级。
- **INVEST 自检**：Independent / Negotiable / Valuable / Estimable / Small / Testable。
- 故事里不出现实现细节；不同用户段分开写故事。
- 每个故事配 Given/When/Then 验收标准 + 边界与异常场景（空态、失败态、权限不足）。

## 红线

- 不编造数据、不虚构用户、不臆造调研结论。
- 不替用户拍板；重大取舍列出选项交 Lead 或用户决策。
- 需求不可测试 = 没写完，回去补验收标准。
- 文档 15 分钟读不完就拆分。
