# 审美与设计评审（design-taste）

封装自 [Leonxlnx/taste-skill](https://github.com/Leonxlnx/taste-skill) v2.5.1
（MIT，上游技能名 `design-taste-frontend`）。上游面向公司站点 / 落地页，自带 Node 22+ 脚本与
真实浏览器检查器；本技能**不整仓 vendoring**，只保留 PM 可执行的部分：页面类型判定、流程、
评审清单、交付物格式与反馈纪律。上游资产与更新方式见 [UPSTREAM.md](UPSTREAM.md)。

本技能是**判断与规格**，不是执行器：PM 没有 shell 工具。需要跑上游脚本或截图时，把命令与
验收标准写进任务交给 Lead / DEV / TSE 执行，并让他们回传原始输出与截图路径。

## 何时加载

- 需求涉及页面 / 界面的视觉、信息层级、交互观感（landing、官网、营销页、应用内界面）
- 要给 DEV 交设计规格，或要对实现做视觉评审
- 用户反馈停留在“不够高级 / 再好看点 / 有点土”这类主观评价，需要转成可执行项

## 一、先判定页面类型（决定用哪套流程）

| 类型 | 判定线索 | 本团队怎么走 |
|---|---|---|
| landing / 官网 / 营销页 / 公司站点 | 目标是说服外部访客：hero、叙事、转化路径 | 用上游完整流程（见第二节）：参考图 → 设计规格 → 浏览器检查 |
| 应用内后台 / 工具界面 / 管理台 | 目标是高频完成任务：表格、表单、详情、状态 | 只用“设计规格 + 评审清单”子集：**不做 shader / 3D / 滚动场景**，不引上游脚本，重点是一致性、信息密度、可读性与状态覆盖（空态 / 加载 / 失败 / 权限不足） |

判定不了时按**低配（工具界面子集）**走，并向 Lead 说明理由。上游的 shader、3D、滚动场景
只允许出现在 software / tech / gaming 类营销页；餐饮、门店、服务、普通实物产品页一律
“照片 + 排版 + 纯色”，不借技术页的视觉花招。

## 二、使用上游（仅营销页需要，可选）

项目里还没有上游时，由 Lead / DEV 执行等价步骤（PM 只提供命令与验收标准）：

```bash
git clone --depth 1 --branch v2.5.1 https://github.com/Leonxlnx/taste-skill .taste-skill
cd .taste-skill/skills/taste-skill
node scripts/start.mjs deal --page <kind>          # 发牌：配色 + 字体配对 + hero 版式
node scripts/consistency.mjs <url-or-file> --page <kind>   # 真实浏览器检查，逐条 PASS/WARN/FAIL
node scripts/gate.mjs                               # 收尾闸门：还有可修 FAIL 就不算完成
```

- `<kind>`：`software` / `gaming` / `tech` / `product` / `service` / `place`。
- 环境：**Node 22+**，以及 Chrome / Edge / Chromium；`CHROME_PATH` 指定非标准安装路径。
- Windows 注意：Node 用 22 及以上；浏览器不在默认位置时，PowerShell 里
  `$env:CHROME_PATH = 'C:\Program Files\Google\Chrome\Application\chrome.exe'`，
  Git Bash 里 `export CHROME_PATH="/c/Program Files/Google/Chrome/Application/chrome.exe"`。
  `ffmpeg` 可选，只在 WebP 输出与 hero 手机裁切时需要。
- 检查器起的是真浏览器：沙箱 / 无图形环境跑不起来时，**降级为按清单人工核对**，并在报告里
  写明“未跑浏览器检查器”，不要假装跑过。不要为了通过检查去改上游文件或检查器。
- 固定版本：只用 **v2.5.1**，不追 main。

## 三、10 条评审清单（评审每条都给 pass / fail / 不适用）

1. **参考图**：有 2–3 张具体参考，且说明每张“借什么”；不是“参考苹果 / 参考线性”这种空话。
2. **单一设计系统**：一套按钮体系、一种卡片样式、一套圆角 / 阴影 / 间距尺度；不混两套风格。
3. **真实照片 / 真实产品 UI**：不用图库假人冒充客户；产品后台用真实界面或等价 HTML UI，
   不拿灰色占位块当“界面已完成”。图片不得带说明性 caption，授权信息放页脚一行。
4. **左右边距一致**：所有内容对齐同一容器边线；不出现一侧贴边、一侧大留白、横向滚动。
5. **每屏一节**：桌面 1440x900 下每个 section 1–2 屏高，标题在顶部，屏内不露出下一节标题。
6. **排版与对比度**：一套字号阶梯 + 一套行高；正文对比度 ≥ 4.5:1；不靠 10px 小字和极浅灰
   撑“高级感”。非技术页禁止紫色 / 淡紫色主视觉。
7. **占位文案**：无 Lorem、无“示例数据 / TODO”、无 `.example` 地址、无编造的评价与数据；
   未定的文案显式标注为假设。
8. **动效克制**：hover / press 有可见反馈；无滚动劫持、无逐节 fade-in、无自动轮播；长动效有
   暂停；`prefers-reduced-motion` 下静止且内容不隐藏。
9. **非 tech 页不用 shader / 3D**：shader、3D、滚动场景只在 software / tech / gaming 页，
   且同时最多 4 个 WebGL 上下文并有静态回退；其它页面用照片、排版与纯色。
10. **三档宽度截图**：桌面 1440、平板 768 / 820、手机 390 各至少一张；无溢出、无重叠、
    无空白可视区、无控件被遮挡。

## 四、交付物（给 DEV 的设计规格）

1. **1 句视觉定位**：给谁、在哪、要什么感觉（例：“给财务新用户的后台账，冷静、密集、
   数据优先”）。
2. **2–3 张参考图**：每张一句话说明借鉴点（版式 / 字体 / 间距 / 动效），标明是参考不是照抄。
3. **设计规格**：配色（含语义 token）、字体与字号阶梯、间距尺度、圆角与描边、动效（时长 /
   缓动 / 触发）、**禁止项**（明确写“不要什么”）。
4. **3 条可执行修改意见**（评审阶段）：每条 = 位置（页面 / 区块 / 元素）+ 现状 + 改成什么
   （具体数值或 token），不写“优化一下”“更精致”。

## 五、反馈纪律

- **不接受“再好看点”“更高级一点”“有点丑”这类反馈**——它既不能执行也不能验收。收到这种
  反馈先追问：哪里不好、对照哪张参考、改成什么；追不出可执行项就标为偏好，不阻塞交付。
- 每条意见都必须可判定（对 / 不对），评审结论落到清单条目，不靠感觉投票。
- 纯主观偏好明确标注为偏好；风格方向有分歧时列 2 个选项交 Lead / 用户拍板，不替用户决定。

## 六、红线

- 不编造参考案例、用户评价、增长数据或授权信息。
- 不用 AI 生成的假图冒充真实产品、门店或团队照片；替身照片必须在报告里如实标注。
- 不为让检查通过而改检查器、改上游文件或隐藏问题；判定为误报就记录理由。
- 需求不可验证 = 没写完；设计规格没有具体数值 / token = 不算交付。
